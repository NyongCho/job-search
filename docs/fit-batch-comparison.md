# 적합도 평가 묶음 비교

목록 평가의 기본 묶음 크기는 3건, 동시 실행은 1개로 정했다. 두 표본에서 3건 묶음은 단건보다 공고당 토큰이 32%, 전체 처리 시간이 28~34% 줄었다. 5건 묶음의 총사용량이 가장 적었고, 첫 결과는 3건 묶음에서 16~20초 빨리 도착했다. 상세 한 건이나 남은 한 건은 더 모일 때까지 기다리지 않는다.

## 실측

2026년 11월 23일에 설치된 Hermes와 `gpt-6.2-astra`로 실행했다. 각 표본에서 같은 경력 사실·평가 기준·JD 순서를 사용하고 묶음마다 빈 세션을 열었다. 각 방식은 한 번씩 실행했다. 3건 방식은 3건과 2건을 순서대로 처리했다. 모든 행에서 공고 5건이 성공했고 실패·재시도는 0건이었다. 입력·출력 토큰은 모델 실측값이며 캐시 읽기·쓰기 토큰은 모두 0이었다.

## 근거 대조

각 표본에는 짧은 JD와 1,500자가 넘는 JD, 같은 회사의 유사 직무가 들어 있다. 공고마다 필수 조건 2개와 대응하는 경력 사실 또는 확인이 필요한 조건을 미리 표시했다. 세 방식 모두 각 표본의 필수 조건 10개를 전부 찾았다. 다른 공고에서 인용한 JD와 다른 공고의 필수 조건을 잘못 가져온 사례는 0건이었다.

- **보류 근거**에서는 세 방식 모두 5건을 보류했다. 3번 공고의 필수 조건인 야간 장애 복구에 대해서도 모두 추가 확인이 필요하다고 판단했다. 일반 업무인 배치 품질 개선은 단건이 충족, 두 묶음이 확인 필요로 판단했다. 지원자의 배치 개발·장애 복구 기록에는 품질을 개선했다는 직접 근거가 없었다. 일부 모델 원응답의 `recommend`와 `needs_review`도 달랐으나 실제 평가기의 보류 판정은 일치했다.
- **80점 경계**에서는 세 방식의 점수와 보류 여부가 공고별로 일치했다. 점수는 1번 90점, 2번 80점, 5번 79.864864…점이었고 3·4번은 보류였다. 선호 밖인 2·5번은 모두 관련 경력이 12개월이고 요구 경력만 36개월과 37개월로 달랐다. 반올림 전 80점을 적용하면 2번만 선호 밖 추천 기준에 든다.

모델이 경험을 미확인으로 표시하고도 질문 문장을 비워 둔 경우가 있었다. 앱은 사용자가 답할 수 있는 업무·우대 경험이 점수 보류 사유라면 검증된 JD 요건으로 질문을 구성한다. 저장해 둔 30개 원응답을 실제 평가·추천 코드로 다시 처리하자, 모집 중이라는 동일 조건에서 각 공고의 추천·확인 질문 분류도 세 방식에서 모두 일치했다.

두 표본은 개인 경력과 운영 공고를 사용하지 않고 만든 고정 사례다. 시간과 토큰은 이 모델과 표본에서 얻은 값이다. 실행 명령과 경력 입력 방법은 설치 안내에 있다. [비교 실행 방법](setup.md#기존-설치에서-적합도-평가-켜기)
